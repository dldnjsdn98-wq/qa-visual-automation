## Minimal proposed private hook and single cleanup ownership

Public `launch_contained` and ordinary calls are unchanged. Private `_launch_windows` gains keyword-only `_diagnostic_owner_sink=None`; when supplied it must be an empty built-in list. Same launcher, interpreter, DETACHED_PROCESS/suspended flags, pipes/null handles, Job1/no-breakaway and WS settings; no copied launcher.

After the existing owner object is constructed, before `_check_limits` or ResumeThread, the diagnostic branch stores the original primary-thread handle on the owner, appends that owner to the sink and returns without resuming. Publication precedes the function's existing `finally` cleanup of attribute storage. This matters because a stalled/failed native cleanup during return must not conceal retained process/Job handles from the supervisor. A post-publication exception delegates termination/handle closure to the supervisor and retains the owner in the helper's failed-launch list; it must not run the ordinary stop/close sequence a second time.

Ownership boundaries:

- Before publication: original helper owns failed-setup cleanup. Harness observes launch completion/error and its cleanup/workload flags; it never issues another stop if setup failed with no published owner. Any pending or ambiguous prepublication creation remains UNKNOWN, not safe no-process. Original native setup calls still lack a proven return-time bound.
- At publication: supervisor owns Job/direct/primary-thread/pipe resources. Publication alone does not authorize resume. Only timely successful launcher return plus complete pre-resume observations allow the receiver to resume. Thus an unwind error/hang permits stop but forbids workload.
- After publication: one stop thread is the sole TerminateJobObject caller. It uses only that retained owned Job; no PID/name/global/parent-Job kill and no helper.stop call. Late publication after a timeout is still watched by this retained stop thread, which requests termination if it receives the owner, but cannot produce timely cleanup proof after the fixed deadline.
- No owner/query/reader handle closes while any tracked launch/observer/receiver/stop thread is alive. Primary thread is closed once, after whole-Job proof and all such workers have ended; then owner.close after setting its stopped state from that proof. Partial or late close is retained/unknown, never a second stop.

This private diagnostic mode intentionally returns an unvalidated suspended owner. It must never be used as a replacement for production launch_contained. It is not approved production instrumentation today. Exact hook ownership/exception paths require independent review and a separate PM claim even though the W1 flag change itself was previously approved.

### Cleanup, snapshot and unresolved cases

The stop thread is independent of observer locks and pipe reads. It requests TerminateJobObject once. For a returned successful request, it checks retained direct-handle signaling and class1 ActiveProcesses0 within the fixed cleanup deadline. Query return after that deadline cannot supply proof. The close worker is allowed only after every tracked worker has ended and timely cleanup proof exists; it must start and finish within the same deadline to supply timely close evidence. Native methods can still block; joins are bounded, not native calls forcibly canceled.

Workers only append completed or unknown event objects to a queue, never mutate the main report/proof booleans. Main filters timestamps, records alive workers, drains available evidence and serializes a fixed snapshot. Later worker completion cannot promote its published classification or proof. A late two-member observation after the snapshot is not claimed absent; alive workers force UNKNOWN/quarantine. Handles/sink/workers/module remain referenced until harness exit, which is explicitly not cleanup proof.

If no owner is published and launcher is still blocked, the stop thread waits for possible late publication without blocking the supervisor. A process whose creation/assignment has not returned cannot be proven stopped by this harness. Harness exit may end pending threads and close OS handles; that does not justify reporting confirmed cleanup of an unassigned/unknown process. This unavoidable preownership native-call uncertainty is explicitly retained for PM, not solved by the private hook. Any failed-setup internal helper cleanup remains separately attributed, without claiming the harness sent a termination request.

Stop/query/close/serialization failures preserve available primary evidence. If the new JSON cannot be written, the already-redacted serialized snapshot is emitted to stderr for parent capture. Filesystem/output I/O and native syscall scheduling are not claimed hard real-time. No per-image process exemption, modified limit, environment expansion, permission escalation or third-party package change is proposed.
